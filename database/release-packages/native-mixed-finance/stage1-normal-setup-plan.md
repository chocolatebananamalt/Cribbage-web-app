# Stage 1: latest normal Setup in the staging preview

This is a proposed plan, not an execution record. No SQL, environment change, grant, deployment, credential lookup or credential creation is performed by these files.

## Scope and fixed target

Use only the reviewed preview branch and its branch-scoped preview environment, against `https://nnhcnvksxgxnpvdqjgpg.supabase.co` (project `nnhcnvksxgxnpvdqjgpg`). The server switch is `EVENT_PRIZE_SETUP_TEST_PROJECT_ENABLED_V1=true`; its absence, any other value, or a different URL denies latest Setup. The code confines the project; preview-branch confinement is an operational restriction on where the switch is assigned, not a branch check in the gate.

This stage admits every currently authorized Director/co-Director in that staging project under the existing tournament role checks. It is not actor-, event-, cohort- or native-rehearsal-confined. It enables latest Setup save, rule-context review, registration activation and exact operation recovery only. It does not enable native routes, ordinary/native Finance, payout, disbursement, publication or actual-money authority.

The rollback-only Main+Con SQL acceptance passed using temporary gates and grants and verified restored catalog/rows and SQL-session exit. That proves the local SQL path, not signed browser/provider operation. Read-only, non-decrypting Vercel metadata confirms the existing sensitive SUPABASE_SECRET_KEY is configured for this preview branch, and the exact staging public URL matches. Its value, validity and real-provider acceptance have not been verified. The new Setup switch is absent and therefore off. Activation uses the existing lazy server-only admin configuration after current identity/role and exact owned preparation checks. No new credential creation is authorized. If that existing configuration is unavailable, stop activation acceptance and report the blocker; do not create or expose a credential to complete this plan.

## Proposed enable sequence

1. Freeze the reviewed application revision, SQL candidate/install provenance and this plan. Keep the existing staging preview and all default-off settings until independent review and explicit rollout authorization are complete. Do not change a global or production deployment environment.
2. Before an authorized SQL change, retain the exact current definitions, owners, ACLs and effective grants of the ten gates and ten public-schema functions listed in `stage1-normal-setup-plan.json`. Confirm the intended staging project and required reviewed SQL closure. A missing or incompatible dependency is a stop condition, not permission to install broader proposals or bypass a guard.
3. In that authorized staging change only, enable the exact ten Setup gates and grant EXECUTE on the nine listed public-schema functions to `authenticated`, and the single finalizer to `service_role`. Do not grant to PostgreSQL `PUBLIC` or `anon`; do not grant private `app` function/table access or general `app` schema USAGE. Preserve every current SQL role/source/lifecycle guard. These are separate server-side changes; the application switch cannot create these permissions.
4. Deploy only the reviewed preview branch with the single server-only switch enabled in that branch's preview environment and the already configured exact staging URL. Do not create a `NEXT_PUBLIC` enablement flag. Keep every native and Finance application/SQL gate at its previously closed value; this stage requires no change to them.
5. Through normal signed-in staging Director/co-Director access, verify that the regular Setup page selects the latest mode and replaces the old regular-prize declaration controls. Verify saved recipient/method/factor/rounding/series readback, explicit rule-context review, registration activation, and exact saved-operation recovery. Retain request/operation identities before a write; reconcile any uncertain outcome before another attempt. Do not claim local SQL acceptance substitutes for this provider/browser proof. No payout or new mathematical policy is part of this stage.
6. Confirm that nonofficial access remains denied, wrong-project or disabled application configuration performs no provider work, and native/Finance routes remain closed. Stop on an unknown write outcome, missing existing server configuration, unexpected grants, or source/role drift. Preserve the exact pending bytes and all committed history.

## Disable and rollback sequence

1. Disable or remove `EVENT_PRIZE_SETUP_TEST_PROJECT_ENABLED_V1` only in the same branch-scoped preview environment. The shared gate then closes page admission and latest save/context/activation/recovery route capabilities together. It does not cancel an in-flight server transaction or prove that a request was not committed.
2. Reconcile any in-flight operation from its exact recorded identity through the authorized recovery process before retrying or replacing it. Preserve device pending data and immutable server rows. If the disabled UI prevents recovery, use a separately reviewed forward repair/recovery deployment; never regenerate operation IDs merely to clear uncertainty.
3. If reverting the authorized staging SQL capability change, restore the exact captured gate definitions and ACL/effective-grant baseline. Do not issue broad grants/revokes, drop candidate tables/functions, delete latest heads, rewrite snapshots, remove receipts, or disable reciprocal legacy guards. Retain evidence of restoration and any unresolved operation.
4. Rolling back the application preview alone is **not** a data rollback. A latest save may have created authoritative latest heads, and the preserved old writers may correctly reject those drafts. Returning to an old preview can therefore leave converted drafts read-only. Forward repair must preserve those heads, histories and exact pending operations; automatic conversion back to legacy or deletion of the new history is outside this plan.

No rollout step has been executed by this document. SQL/permission changes, preview environment assignment and deployment remain separate authorization boundaries.
