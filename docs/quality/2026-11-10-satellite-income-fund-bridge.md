# Satellite Income and Recorded-Fund Review Bridge

Local implementation only; SQL unexecuted, not a registered migration, default-off/revoked. No fixture, hosted write, public upload, denied retry or money movement.

Implemented separate immutable Satellite income records (add/correct/void) and declared fund reviews. Shared unrestricted-income roots reserve physical evidence/reference ownership after voids. Reciprocal guards cover historical ordinary receipts, costs, Q/Side records, addons and the Main/Con versus optional versus Satellite income domains. Current source requires event activation, native current allocation and complete journal lineage; orphan/foreign journal sources hold instead of meaning zero. Saved review binds the entire allocation/activation/income capture and current heads, with actual primary-Director actor/session, global operation nonce, reason, immutable receipt and audit. Changed income/allocation invalidates review. Local UTC pins and JS-compatible text validation preserve stable readable captures. These are source-level safeguards, not proven database execution.

Fund equation uses only this event's allocated regular entry receipts minus player benefits/costs plus its own unrestricted additional income. Pool and sibling money is excluded. Reviewed zero is explicit, not inferred from missing rows. Current positive income requires recorded_complete. The existing completion reader accepts only a current declared review with identical allocation capture; otherwise it retains its hold. This is Director-declared recorded coverage, never independent asset/bank verification, solvency certification, payout approval or a comparison-calculator award. Ties, inconsistent results and entered-award shortfalls remain held.

A read-only Director section is wired locally into Satellite Results behind its literal false gate. It shows saved income/voids and separate fund amounts, current versus stale declaration and unknown source fallback. Normal cookie provider verifies actual primary-Director access before and after data, not a role string or service impersonation. Co access is not expanded. The old allocation-only comparison now explicitly says it excludes separately recorded additional income, avoiding a conflicting statement when the new review exists.

Remaining implementation: safe retained-request income-entry/correction/void and review-confirmation controls plus same-origin mutation/recovery endpoint; source-level native writer exists, but these controls are not wired. Current native allocation is required; existing allocator forbids negative entry-minus-cost baseline, so a case funded only by later donations cannot bootstrap through this bridge yet. No hidden substitute allocation or borrowing is allowed. New completion SQL depends on the bridge function being present before enablement.
