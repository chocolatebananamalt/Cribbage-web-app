# Expense recovery and fresh recorded-fund review — local candidate

## Acceptance and scope

Preserve all earlier recovery keys and bytes, including other accounts, malformed legacy copies and unknown server outcomes. A new expense must retain the complete exact payload before POST, use empty-slot/byte comparison before replacing or removing anything, and fence async work by actor/tournament/activation. A legacy digest is not a complete request; do not invent missing details or treat a null reconciliation as proof that an action never committed. Only exact authenticated terminal evidence plus explicit supported archival/cleanup may release its own operation.

After recorded-cost adoption, load current supported native playoff, proposal, allocation, recorded-income and sanctioning evidence for a new explicit fund-completeness review. Sanctioning remains inside recorded event costs and is never subtracted again. Keep proposed income distinct from recorded bookkeeping, and unknown/incomplete history distinct from explicit zero. Require one current eligible expense event for positive sanctioning coverage; do not combine unrelated expenses. Preserve final award/payment safeguards and keep all new provider/page/SQL gates disabled.

Allowed tests use synthetic data and disposable network-isolated local databases only, with verified cleanup. No hosted reads/writes, publication, real funds, invitations or role changes. Actual Supabase cookie/provider-session acceptance is a separate gate. Local role/JWT-context simulation does not prove independent humans or physical games.

## Implementation and verification notes

The expense slice replaces cross-account key cleanup and digest-only new requests with fixed-scope exact-payload recovery while retaining original legacy envelopes unchanged. The new fund source is read-only and privately guarded, with an authenticated-only public wrapper behind literal-false gates. It reuses completed native game/recipient proof, income lineage and existing single-expense coverage logic. It does not replace the fund writer or create a new award authority.

Fund review has a separate exact-operation outbox and explicitly loaded UI. Its ten-key request pins proposal, allocation, income head, review version and selected expense. Lost/ambiguous replies remain pending until checked; exact fresh review/source readback is required before accepted receipt archival. Unknown/conflicting rejection codes cannot release pending work. The reviewed two-field early rejection list is limited to writer/helper branches that return before operation insertion, with SQL-subtransaction rollback covering invalid numeric/text exceptions. A stale review may be archived explicitly into history; no payment is claimed.

Source review found two outbox issues (fully bound rejection bypass and terminal income-head integer bound); both were corrected with regressions. React compiler checks led to moving IO ownership into an inactive fixed-scope session with independent epochs, rather than evaluating ref-dependent constructor callbacks during render.

The first disposable attempt failed on unsupported Node strip-only constructor syntax before database setup; its container was removed and independently confirmed absent. The next run reached full qualification, adoption, verified native playoffs and supported income recording, but the new reader rejected its own output. Investigation identified an implementation error: actual native regular-entry sources are `entry_receipt`, not `receipt`. SQL, browser decoder and synthetic fixtures were corrected to that exact existing tag, with a regression rejecting the wrong spelling. The failed run and cleanup remain preserved. New diagnostics export source bytes before assertions so a later failure can be investigated offline.

## Deliberate limits

- The existing fund writer requires supported completed native four-/five-qualifier playoffs. The new source does not relax that condition for pre-playoff, paper/mixed or larger brackets.
- Recorded income is bookkeeping evidence, not independent proof of bank receipt. Proposed and actual payout amounts remain separate; the fund review does not approve final awards or move money.
- Browser recovery-key preflight is not an atomic cross-tab reservation. Server source/version checks remain authoritative, and unrelated device copies are never deleted.
- A final read-only source check found the analogous old `clearOtherActors`, digest-only and null-reconciliation cleanup in `payments/payment-client.tsx`. It was not changed in this expense/fund slice. The standalone disabled fund page does not mount that component; the existing combined Payments page does. Do not infer that unified payment navigation is safe from the isolated ExpenseClient browser proof. Fix or safely isolate legacy payment recovery before enabling that navigation.
- Actual provider sessions, account switching/role loss under real cookies, hosted installer ownership/RLS, staging recovery and approved deployment remain outside these local proofs.
