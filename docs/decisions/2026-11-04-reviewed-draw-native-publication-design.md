## Locking blocker found from actual source
Native 0047 publish_initial_seating takes native actor/op advisory lock then tournament FOR UPDATE. Random-draw proposal also locks tournament. But 0205 set_roster_entry_active_status_v1 starts with roster FOR UPDATE, then inserts an operation receipt referencing tournament. Full random source binding includes lifecycle/check-in/preference/account-link/setup versions, even excluded roster entries. Merely locking tournament does not stop every source change; blindly adding roster FOR UPDATE after it can deadlock with child FK KEY SHARE acquisition.

A candidate protocol for evaluation is tournament FOR NO KEY UPDATE first (allowing FK KEY SHARE), current role and all roster rows FOR SHARE in deterministic order, then tournament upgrade to FOR UPDATE and a second roster capture/lock for intervening inserts. FOR SHARE blocks explicit roster FOR UPDATE/mutation while allowing ordinary child FK KEY SHARE. This is a proposal, NOT a proven solution: all writer paths, child updates and competing native/manual/draw/role operations must be traced and tested. Do not implement or enable a transaction claiming concurrency safety from a source-only review.

Additional cross-operation risk: 0204 correct_tournament_public_contact_v1 takes tournament FOR UPDATE before the global actor/op advisory lock, opposite native 0047. Reusing a nonce across those operations can deadlock. The runtime suite must include cross-operation nonce reuse, refuse prior-receipt adoption and prove rollback; no existing writer is changed in this checkpoint.
